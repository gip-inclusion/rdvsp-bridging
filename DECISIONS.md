## Product

   plus a minimal admin page, not a self-service portal.

   The data model is already Account (company) → Connections (user ↔ agent).
3. **(you)** Busy rules: activities owned by the connected user with `busy` true or null, done or not; activities

## Technical

1. **(me)** Ruby 4.0.7 (latest GA; 4.1 is preview) via rv 0.7.1 (Homebrew). Rails 8.1.4.
2. **(me)** RSpec + FactoryBot, RuboCop (+rails, +rspec) with a config merged from RDV-SP (metrics cops off,
   `frozen_string_literal: never`, trailing commas) and RDVI (120 columns). Brakeman, bundler-audit kept.
   `strong_migrations` like RDV-SP.
3. **(me)** Local Postgres 17 in Docker (OrbStack) on 127.0.0.1:5442 to avoid clashing with a local RDV-SP; configured
   through libpq `PG*` env vars in `.env` so `database.yml` stays stock.
4. **(me)** Local mirror + change log rather than pass-through to Pipedrive. Reasons: RDV-SP polls up to once a minute
   per agent and ignores pagination; Pipedrive v2 has **no due-date filter** (`due_date_from` is rejected) and
   **deleted activities disappear from listings even with `updated_since`** (verified), so deletions can only be seen
   through webhooks or a full diff.
5. **(me)** Sync tokens never fail: `<generation>-<seq>`; anything unparseable, from another generation or older than
   the tombstone horizon returns the full state plus all tombstones. No 507, ever.
6. **(me)** Freshness: incremental refresh (`updated_since`) triggered when RDV-SP polls if the account wasn't
   refreshed in the last 60 s, plus every 5 min by cron, plus Pipedrive webhooks (when publicly reachable); full diff
   per connection every hour to catch deletions missed by webhooks. Webhook payloads are only a trigger: we re-fetch
   the activity (`GET /api/v2/activities/:id` still returns deleted ones with `is_deleted: true`).
7. **(me)** RDV writes are asynchronous: the CalDAV `PUT` answers immediately (201/204 + absolute `Location` + ETag)
   and a GoodJob job creates/updates/deletes the Pipedrive activity with retries. Idempotent on (connection, href).
   The RDV payload is stored encrypted until pushed, then cleared.
8. **(me)** `STATUS:CANCELLED` on a PUT (RDV-SP cancels by updating) deletes the Pipedrive activity, same as DELETE.
9. **(me)** Busy blocks exported to RDV-SP carry no subject or note: `SUMMARY:Occupé`, start/end in UTC,
   `TRANSP:OPAQUE`. Window: 7 days back to 6 months ahead.
10. **(me)** CalDAV credentials: random username + password generated by the bridge, password stored with bcrypt;
    the connection is derived from the credentials and any URL for another connection is a 404.
11. **(me)** Times: Pipedrive `due_date`/`due_time` are UTC (verified: a 10:00 Paris meeting reads `08:00`).
12. **(me)** Puma refuses WebDAV methods by default (501 on `PROPFIND`): `config/puma.rb` allows
    `PROPFIND PROPPATCH REPORT MKCALENDAR`. Without it, nothing works in production.
13. **(me)** RDVs received from RDV-SP are never listed in the calendar (PROPFIND Depth 1, calendar-query,
    sync-collection), so we don't rely on RDV-SP's "skip URLs of our own RDVs" filter; `GET` on them still works.
    Their Pipedrive activities are excluded from busy times (by id and by activity type).
14. **(me)** Without `usager_details`: subject is RDV-SP's non-sensitive `RDV <motif>` when it has that shape,
    otherwise "RDV Service Public"; location only when it is a URL (visio). Lieu addresses are dropped too, because
    with RDV-SP's "données sensibles" option the location can be the usager's phone number or home address.
15. **(me)** Person linking is best effort: the CalDAV event carries no usager e-mail or phone, only the name in the
    summary (when RDV-SP's sensitive option is on) and the phone as location for phone RDVs. We link to an existing
    Person only on a single exact name match, else create one. Reliable linking would need RDV-SP's organisation
    webhooks or API — a later option.
16. **(me)** When Pipedrive fails we keep serving the mirror (no 503): RDV-SP keeps its last imported events anyway,
    so a 503 would only add noise to *their* Sentry. We alert instead (after 1 h, then daily).
17. **(me)** Without public webhooks (local dev), deletions in Pipedrive are seen by the hourly rebuild. A rebuild on
    every RDV-SP poll would cost ~5k Pipedrive units/day per connection; the daily budget is 150k per company.
18. **(me)** RDV-SP's connection test event (`rdvsp-connection-test-*`) is acknowledged and never stored or forwarded.
19. **(me)** Never stored: provider subjects/notes and raw ICS bodies. The RDV payload (summary/description/location)
    is stored encrypted until pushed to Pipedrive, then cleared.
20. **(me)** End-to-end validated against `rdv-service-public@production` (8a20a75, 14 Oct 2026) with RDV-SP's own
    controller check, import/export jobs and slot calculator (`script/e2e/`). Note: on `production`, CalDAV settings
    moved to a `CaldavConfig` model and the connection check now **requires a `sync-token`** — your local checkout
    (branch `online-booking-email-sans-confirmation`, July) predates that.
21. **(me)** Configuration is env-only (no `credentials.yml.enc`, removed): simpler on Scaleway. `/up` is excluded
    from the SSL redirect; test gems are left out of the image. Sentry never sends request bodies
    (`send_default_pii = false`). Production image verified locally (boot, migrations, cron, WebDAV methods).
    Build with `--platform linux/amd64` for Scaleway.
22. **(you → me)** Google spike done as a **second provider** (Calendar REST API + OAuth) rather than a CalDAV
    passthrough: no XML rewriting, and RDV-SP only ever sees start/end times. Specs only (no OAuth client yet):
    see `docs/google.md` for the 10-minute setup to try it live. Deletions via `updatedMin` + `showDeleted`.
23. **(me)** Provider "interface" is still a convention, not a class hierarchy: `Providers` dispatches to
    `<Provider>::RefreshAccount`, `RebuildConnection`, `PushRdv`; content rules shared in `RdvContent`. Two
    providers now share the CalDAV core, sync tokens, mirror, jobs and admin; worth formalising only if a third
    one (Salesforce) shows the same shape.
24. **(me)** `.ruby-version` holds `4.0.7` (not `ruby-4.0.7`) so rbenv users aren't stuck; rv reads both.
