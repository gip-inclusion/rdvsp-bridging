## Product

1. **(you)** No partner yet: build against our Pipedrive sandbox and a local RDV-SP. Onboarding through rake tasks
   plus a minimal admin page, not a self-service portal.
2. **(you)** Pipedrive access: one admin API token per company for the pilot; private OAuth app is the next milestone.
   The data model is already Account (company) → Connections (user ↔ agent).
3. **(you)** Busy rules: activities owned by the connected user with `busy` true or null, done or not; activities
   without a time (all-day) are ignored unless the connection's `include_all_day` toggle is on (then they block the
   whole day, Europe/Paris); missing duration = 30 min; activities created by the bridge are never exported as busy.
4. **(you)** RDVs in Pipedrive: minimal by default, dedicated activity type "RDV Service Public". Two per-company
   options: `usager_details` (title/description/location passed through as RDV-SP sends them) and `link_persons`

5. **(you)** Pipedrive edits/deletions of an RDV activity are ignored (RDV-SP is the source of truth), but the
   activity note always carries the RDV-SP links to cancel or move the RDV.

## Technical

1. **(me)** Ruby 4.0.7 (latest GA; 4.1 is preview) via rv 0.7.1 (Homebrew). Rails 8.1.4.
2. **(me)** RSpec + FactoryBot, RuboCop (+rails, +rspec) with a config merged from RDV-SP (metrics cops off,
   `frozen_string_literal: never`, trailing commas) and RDVI (120 columns). Brakeman, bundler-audit kept.
   `strong_migrations` like RDV-SP.
3. **(me)** Local Postgres 17 in Docker (OrbStack) on 127.0.0.1:5442 to avoid clashing with a local RDV-SP; configured
   through libpq `PG*` env vars in `.env` so `database.yml` stays stock.
4. **(me)** Local mirror + change log rather than pass-through to Pipedrive. Reasons: RDV-SP polls up to once a minute
   per agent and ignores pagination; Pipedrive v2 has **no due-date filter** (`due_date_from` is rejected) and
   **deleted activities disappear from listings even with `updated_since`** (verified), so deletions can only be seen
   through webhooks or a full diff.
5. **(me)** Sync tokens never fail: `<generation>-<seq>`; anything unparseable, from another generation or older than
   the tombstone horizon returns the full state plus all tombstones. No 507, ever.
6. **(me)** Freshness: incremental refresh (`updated_since`) triggered when RDV-SP polls if the account wasn't
   refreshed in the last 60 s, plus every 5 min by cron, plus Pipedrive webhooks (when publicly reachable); full diff
   per connection every hour to catch deletions missed by webhooks. Webhook payloads are only a trigger: we re-fetch
   the activity (`GET /api/v2/activities/:id` still returns deleted ones with `is_deleted: true`).
7. **(me)** RDV writes are asynchronous: the CalDAV `PUT` answers immediately (201/204 + absolute `Location` + ETag)
   and a GoodJob job creates/updates/deletes the Pipedrive activity with retries. Idempotent on (connection, href).
   The RDV payload is stored encrypted until pushed, then cleared.
8. **(me)** `STATUS:CANCELLED` on a PUT (RDV-SP cancels by updating) deletes the Pipedrive activity, same as DELETE.
9. **(me)** Busy blocks exported to RDV-SP carry no subject or note: `SUMMARY:Occupé`, start/end in UTC,
   `TRANSP:OPAQUE`. Window: 7 days back to 6 months ahead.
10. **(me)** CalDAV credentials: random username + password generated by the bridge, password stored with bcrypt;
    the connection is derived from the credentials and any URL for another connection is a 404.
11. **(me)** Times: Pipedrive `due_date`/`due_time` are UTC (verified: a 10:00 Paris meeting reads `08:00`).
