## Security audit (2026-10-22)

29. **(you → me)** Fixes from the audit (code review, local pentest, black-box checks of nova):
    - Puma refuses bodies over 1 MB (413): requests carry a few kilobytes, and parsing a large JSON body could exhaust
      the 1 GB container before any authentication.
    - Pipedrive webhooks authenticate with HTTP basic auth (user `rdvsp-bridging`, password = the account's webhook
      token), checked before the body is parsed; the token is no longer in the URL, hence no longer in the logs.
      Onboarding replaces this bridge's existing webhooks, since Pipedrive never returns the password. Webhook
      `data`/`previous` are filtered from the logs (they carry the activity's subject, note and participants).
    - Links are taken only from the description before RDV-SP's free-text `Contexte :`, which could otherwise smuggle
      usager data (or any link) into the partner's tool without `usager_details`.
    - CalDAV passwords are digested with SHA-256 instead of bcrypt: they are 32 random characters, so bcrypt only made
      every RDV-SP request cost ~250 ms of CPU and leaked whether a username exists. Bcrypt digests are upgraded on
      the next successful login (bcrypt stays in the Gemfile until then).
    - **(you)** No lockout after failed CalDAV logins: guessing a 187-bit random password online is hopeless anyway,
      while a lockout would let anyone who knows a username stop that agent's sync, and would lock out RDV-SP
      still polling with the old password right after a reset. Per IP is not an option either (one RDV-SP instance
      serves all its agents from the same addresses). A leaked password is handled by a reset from the admin.
    - `/admin` is rate limited (30 requests per minute, wrong passwords included).
    - `BRIDGE_BASE_URL` is the only source of public URLs (`config.x.base_url`) and, in production, the only allowed
      host (`Host` and `X-Forwarded-Host`; `/up` excluded for the platform's probes).

## RDVs that existed before the connection (2026-11-10)

30. **(you → me)** The sync is for RDVs booked **after** the agent connects. RDV-SP PUTs every RDV from two weeks back
    when the agent saves their CalDAV settings, and the first partner's agent already had them all in their calendar:
    27 duplicates. An RDV is now classified once, at the first PUT of its href, as *ignored* (`rdvs.ignored_at`) when
    it arrives in the start-up window (opened by each connection test, closed after a minute without a never-seen RDV,
    at most 15 min) or when its RDV-SP id (from the "Voir sur" link) is at or below the highest one ignored on the
    connection (catches late retries and older RDVs touched later). Ignored RDVs are stored and answered as before but
    keep no content and never reach the provider; an activity they still have is removed. The ICS has no booking date,
    hence the heuristic; design and product answers in `docs/preexisting-rdvs.md`. Known limits: an RDV booked in the
    minute after a connection test is ignored (admin: "Transmettre quand même", pushed at its next change), and a bulk
    export delayed past the window is pushed (admin: "Ignorer les RDV reçus avant…", with a preview). Amends Technical
    18 (the connection test's time is now recorded) and narrows Product 5 to RDVs that aren't ignored.
31. **(me)** Pipedrive doesn't answer 404 for a deleted activity: `PATCH` gets **403** "Cannot update a deleted
    activity." (which our client read as a refused token) and `DELETE` gets **400** "Activity is already deleted"
    (verified 2026-11-10). So the "recreate it" of Product 5 never worked in production. `PushRdv` now re-fetches the
    activity when a `PATCH` or `DELETE` fails: deleted means gone, anything else is raised as before.
32. **(me)** The admin had no French translations (`time_ago_in_words` showed "Translation missing"): Rails' French
    translations are in `config/locales/fr.yml` as in RDV-SP, and missing translations raise in development and test.
33. **(me)** Rails 8.1.4.1 rejects requests whose `Forwarded` and `X-Forwarded-For` headers name different clients.
    Scaleway's load balancers forward from 100.64.0.0/10 and leave the last hop out of `Forwarded`, so every CalDAV
    and webhook request failed after the deploy of 2026-11-10 (16:47 to the fix). That range is now a trusted proxy:
    both headers then name the real client, which `remote_ip` (and the admin rate limit) now returns.

    bridge's OAuth application at RDV-SP prepares the use of RDV plans. The bridge now holds an RDV-SP credential: an

    `grants_autonomous_signup` off. Staff choose the organisation, the Pipedrive field option that marks a beneficiary
    and an activity date, see a preview (counts only), then a job creates the usagers with an `external_reference` to
    the Pipedrive person. Persons whose e-mail, phone or full name an organisation's usager already has are left out:
    agents had created some by hand, and a homonym left out is better than a duplicate. The bridge keeps person id ↔
    usager id, no personal data. One-off, re-runnable; no continuous sync (`docs/rdvsp-usager-import.md`).
37. **(you → me)** A "Prendre RDV" link action on the person's page in Pipedrive (a private app in the Developer Hub,
    JWT-signed clicks) opens an RDV-SP RDV plan for that person: the bridge finds their usager, transferring them on
    the fly with the import's rules if needed, creates the plan with the usager's id (never `external_id`, whose lookup
    RDV-SP had broken) and redirects to it. A same-name usager without the same e-mail or phone is not used: the agent
    books in RDV-SP. Plans belong to the agent who authorized the bridge, so only they can use the button for now
